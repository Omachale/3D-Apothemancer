# Design goals

Standing context for this project, so it does not have to be re-explained each
session. `README.md` covers how the code works; this file covers *why* and
*what next*.

## What this is for

A sandbox for trying out game rules that have not been designed yet. The
specific things to be experimented with:

- a magic-casting system
- damage types
- basic physics
- graphics — both what the engine can do and what can be built by hand

The world exists to support that experimentation. It is not the product.

## Constraints that shape every decision

- **The owner is not a coder and not a graphic artist.** Explanations should be
  in terms of what happens on screen and what knob changes it, not in terms of
  code structure. Prefer exported, tunable values over things that require
  editing scripts.
- **Rules will change repeatedly.** Anything encoding a game rule should sit
  behind a clear seam so it can be thrown away without disturbing movement,
  camera or terrain. `spell_caster.gd`'s `cast_released` signal is the model
  for this: timing lives in the character, consequence lives elsewhere.
- **Stand-ins are acceptable and expected.** Placeholder art that reads clearly
  beats nothing. Say plainly when something is placeholder.
- **Assets come from free packs or procedural generation**, not from
  hand-modelling.

## Feature status

**1. Spell-casting animation — done (placeholder).**
WINDUP → RELEASE → RECOVER → COOLDOWN, on left click or Space, with a glowing
orb at the casting hand. `cast_released(origin, direction)` fires at the moment
a projectile should spawn; nothing consumes it yet. See README for the tunable
values.

**2. NPC — assets in and moving; combat not started.**
Two characters are in the world and wandering: `Witch` and `Medieval` (an
armoured knight), at (6, 0, 16) and (14, 0, 16). Both are Quaternius-style
exports sharing one 62-bone rig and one 24-clip animation library, so
`npc_wander.gd` drives both without modification and any future character
with the same export shape will work too.

The Witch now throws a bolt of dark energy at the player on sight, which
**knocks them back and nothing else** — no health, no damage, anywhere. That
is a real, readable interaction that commits to none of the undecided magic
rules; damage hangs off `projectile.gd` when those rules exist. The Medieval
knight still only wanders (`attack_enabled` is off).

The clips already available on both, for when combat does arrive: `Idle`,
`Walk`, `Run` (+ `Run_Left/Right/Back`), `Death`, `HitRecieve` (×2),
`Punch_Left/Right`, `Kick_Left/Right`, `Sword_Slash`, `Roll`, `Interact`,
`Wave`. That is the whole combat set already made — wiring an `AnimationTree`
to a state machine, not authoring poses.

**3. Multi-level building with internal stairs — done (placeholder).**
A three-storey stone keep at (-26, 0, -14), generated by `building.gd` from
exported numbers — storeys, height, footprint, door and window sizes, stairs.
Changing the number of floors is changing one number. Walk in the door, climb
two flights to the top. Storeys above the player and walls facing the camera
are hidden while inside, giving the ARPG cutaway.

Function was prioritised over form here as asked. It is boxes and a procedural
masonry shader; there is no furniture, no interior detail and no roof access.

## Wind-swayed vegetation

Grass is in: three patches (~95k blades, three `MultiMesh` draw calls, 145
FPS — rendering is nearly free). The real cost, and the thing that actually
limits patch size, is *placement* time at load — one raycast per candidate
blade, logged per field. All three place in well under half a second
combined; blanket-covering the whole map instead of using patches would mean
a million-plus rays and a load stall, which is why patches stay the approach
even though rendering headroom would allow much more.

Wind is a **global shader uniform**, not a per-material setting, set by the
`Wind` autoload (`scripts/world/wind.gd`) rather than owned by the grass
shader. This was a deliberate decision made *before* building grass,
specifically so trees can be added later without migrating anything: a tree
shader declares the same `global uniform` names and is automatically swaying
in sync with the grass, in the same gusts, at the same moment. Do not add
per-material wind parameters to a new swaying thing — read the globals.

**The wind model went through a real redesign, not a tuning pass.** The first
version was one continuous sine wave and it looked wrong for a specific
reason: everything was always moving, so there was no calm to contrast a gust
against — it read as constant random wriggling rather than weather. Rebuilt as
two layers: a tiny always-on idle jitter (the "alive" sway), and separate
travelling gusts — a Gaussian bend positioned along the wind axis, its centre
a function of time alone, so the same peak sweeps across every field in the
world simultaneously rather than each patch pulsing independently. Verified by
watching one fixed location go calm → visibly bent → calm across a single
gust's passage, not just by reading the shader math and assuming it worked.

Ground also got redone alongside this: the original checker-grid shader tiled
visibly, more so once grass sat on it and bare ground showed at patch edges.
Replaced with world-space value noise (`ground_meadow.gdshader`) — no
repeating unit, so nothing for the eye to lock onto.

**When tree sway is built**, the harder part will not be the wind math (same
technique: bend weighted by height, root fixed) — it will be coordinating two
separate meshes (trunk, canopy) so the canopy sways more than the trunk, in
the same direction, with a bit of phase lag, rather than each moving
independently. Trees are not instanced (only a dozen or so), so no
MultiMesh work is needed there, unlike grass.

## Cloud shadows — abandoned, needs a different approach

Rain, lightning and sun-dimming all shipped and work. Moving dark cloud
shadows across the ground/grass did not, after many attempts, and the code
for it has been removed (was `cloud_coverage` global uniform, `cloud_test_*`
uniforms and the `cloud_*` functions in `grass.gdshader` and
`ground_meadow.gdshader`, plus the coverage plumbing in `rain.gd`). The
`git log` history for those two shader files has the discarded attempts if a
future session wants to see exact code rather than just this summary.

**The actual goal:** a soft, irregular, blob-shaped patch of darkening that
drifts across the field with the wind, no visible edge shape.

**What was tried, in order, and why each failed:**
1. **Single-octave bilinear value noise, thresholded with `smoothstep`.**
   Drew a near-straight edge. Cause: at the chosen scale, the visible ~40-60
   unit view only ever showed part of *one* noise cell, and a bilinear surface
   is locally a plane — thresholding a plane draws a straight line.
2. **More octaves of the same value noise.** Softened the edge slightly but
   did not fix it, because value noise's bilinear interpolation formula
   (`a + (b-a)u + (c-a)v + (a-b-c+d)uv`) has level sets that are hyperbolas
   whose asymptotes run parallel to world X and Z *regardless of scale* —
   every octave shares that same axis-aligned skeleton, so stacking more of
   them reinforces the artifact instead of hiding it. This is a structural
   property of value noise, not a tuning problem.
3. **Perturbing the `smoothstep` threshold with summed sine waves,** to try to
   wobble the edge. Made it worse: `sin()` of a linear function of position
   has *perfectly straight* level sets of its own, so this added a second,
   independent source of straight lines on top of the first.
4. **Switching to gradient noise** (dot products against random per-corner
   directions, i.e. real Perlin/simplex-style noise) with 3 rotated octaves
   and domain warping. This genuinely fixed the axis-aligned-straight-line
   problem — no more crossing lines. But then:
5. Ran into a **second, different bug**: the test area was sized so the whole
   visible patch sat inside roughly one noise cell of the dominant octave,
   so instead of a straight line it showed that one cell's smooth, roughly
   diamond-shaped centre. Fixed by increasing `cloud_scale` so several cells
   spanned the visible area.
6. Even with multiple cells visible, the result still read as "a mix of odd
   polygons" rather than organic blobs — some segments of the boundary were
   still visibly straight over a noticeable distance. Root cause not fully
   diagnosed; plausibly the level sets of low-octave-count gradient noise
   still have long near-straight runs between curvature changes at this
   scale, and 3 octaves plus one round of domain warp was not enough to hide
   it. Not investigated further.
7. **Removed the threshold entirely**, using the raw (warped, multi-octave)
   noise value directly as a continuous darkening amount instead of a
   thresholded shape — reasoning that if nothing is ever "inside" vs.
   "outside" a boundary, there's no edge to look wrong. Also looked bad and
   still showed a fairly straight edge, which was not fully explained before
   the effort was abandoned — worth understanding why before trying again,
   since it undermines the theory that thresholding was the whole problem.

**Ideas not yet tried, for a future attempt:**
- **A hand-authored, tileable, low-res grayscale cloud texture, scrolled over
  time**, instead of computing shape from noise at all. This is closer to
  how simple commercial weather assets actually do it — no runtime shape
  math means no shape-math bugs. Would need either a downloaded/generated
  texture or a small offline script to bake one (e.g. blurred blob shapes
  composited in an image tool), which is a different kind of work than
  shader tuning.
- **Worley/cellular noise** instead of Perlin-style gradient noise — genuinely
  different level-set geometry (cell boundaries, not smooth ridges), might
  break up the residual straightness point 6 ran into. Not implemented in
  Godot by default; would need writing from scratch.
- Actually rendering a **small number of soft round decals/sprites** (additive
  darkening blobs with a radial falloff, no noise at all) moving independently,
  rather than one continuous noise field. Cheap, guaranteed no straight edges
  by construction, at the cost of looking less "natural"/irregular.
- Before any of the above: get an actual diagnosis of *why* step 7 (no
  threshold at all) still showed a straight edge. If a plain continuous noise
  value can still produce a visible straight edge, something more
  fundamental than thresholding was misunderstood, and it is worth finding
  that before investing in a new technique that might inherit the same bug.

## Things learned that are easy to forget

- At the gameplay camera distance the character is ~100px tall and the hat
  hides the body. **Effects read; poses do not.** Spend effort on projectiles,
  lights and ground decals rather than on bone animation. Use `F1` to inspect.
- The Mage rig is T-posed in bind pose, which makes arm animation
  counter-intuitive. See the AXES note in `player_animator.gd`.
- Screenshots are not sufficient to verify an animation — the robe hides the
  limbs. Use the harness's `--log` hand readout.
- A staircase's collision is a solid wedge, so its bottom step needs clear
  floor in front of it or the flight cannot be walked onto at all. Easy to get
  wrong and it looks fine in a screenshot.
- Procedural world-space materials (the masonry shader) are a cheap way to get
  convincing surfaces without texturing or UV work. Worth reaching for again.
- Seeing into a building is a **clip plane** problem, not a transparency
  problem. Alpha fading overlapping interior geometry sorts wrong and loses
  shadows; discarding fragments above a moving plane does neither. Ceilings and
  walls need *separate* planes — see the note in `building.gd`.
- A continuous height clip and a discrete "which storeys are even eligible"
  gate are two different mechanisms and both are needed. Skipping the gate is
  what let distant storeys fade in with nothing under them — a real bug found
  by actually walking through the building, not visible from any screenshot
  taken standing still.
- Near walls should be cut to a low stub ("kneewall"), not hidden outright —
  hiding a wall takes its doorway with it, since a doorway has no geometry of
  its own to stay visible when the wall around it vanishes. Standard technique
  (The Sims, most isometric RPGs).
- Not every upright can share one reveal rule. A flight of stairs needs a
  *tighter* eligibility gate than a wall does, because a partially-revealed
  wall still looks like a wall (it's grounded at the true floor height
  regardless), while a partially-revealed staircase looks broken (its treads
  only exist between the two storeys it connects, so showing some without the
  landing floor is geometry with nothing under it).
- Godot treats **clockwise**-wound triangles as front-facing. Getting a
  generated mesh backwards produces two symptoms that look unrelated — the
  surface renders near-black (normals face away from the light) and the player
  cannot stand on it (`is_on_floor()` stays false, because the collision
  normal points down too). One cause. Cost an hour on the hill.
- An external impulse (knockback) has to be tracked as its own value and
  summed into `velocity`, never derived by subtracting it back out.
  `velocity` is whatever `move_and_slide` last left there, and on the frame a
  hit lands it does not contain the impulse yet — subtracting injects a
  phantom opposite velocity and the player gets shoved *toward* the attacker.
- Procedural terrain steepness is a hard constraint, not a taste question: the
  player's `floor_max_angle` (50 degrees) caps it, and for a smoothstep
  falloff the steepest slope is `1.5 x height / radius`. Height and radius
  cannot be chosen independently.
- A capsule collider's centre must sit at *half its height*, not at a fixed
  1.0. Getting this wrong sinks the character into the ground by the
  difference — the Medieval knight (1.9 tall) floated 5cm under until its
  collider was recentred at 0.95. Invisible in a screenshot; obvious the
  moment the NPC log printed `y = -0.05`.
- Check a new NPC's spawn position against the terrain footprints in
  `zone.gd` before placing it. The Hill spans x ∈ [-2, 38], z ∈ [-32, 8] and
  will silently swallow anything spawned inside it.
- The dev harness's `--at` teleport does not raycast onto terrain — it sets a
  bare Y coordinate. On sloped ground (the mound) an `--at` below the true
  surface height there drops the character through to whatever flat plane is
  underneath instead of resting on the slope. Spawn above the expected height
  when testing anything on the mound.
- A fragment-shader clip/discard does not automatically clip the shadow it
  casts — the shadow pass uses the underlying mesh, uncut. Two symptoms that
  looked unrelated (self-shadow streaking at a clip seam, and a shadow left
  behind by a wall that had been hidden) turned out to be the same bug. Fix:
  turn shadow casting off for anything that gets clipped this way.
- Some "rendering" problems are really layout problems. Stacked staircases
  could not be fixed by any reveal trick; the flights had to be moved apart.
- Adding a `class_name` to a script does not register it until the project is
  rescanned: `godot --headless --path . --editor --quit`.
- **A vertex displacement can be mathematically perfect and still invisible if
  it happens along the camera's view axis.** Grass wind appeared completely
  broken across several sessions: the wind direction (32 degrees) sat 13
  degrees from the default camera yaw (45), so blades leaned almost directly
  away from the viewer and a real 0.24-unit lean produced roughly *three
  pixels* of on-screen motion. Every number in the shader was correct the
  whole time. Keep the prevailing wind roughly perpendicular to the default
  camera yaw. Before hunting for a bug in a "not working" visual effect, check
  whether it is merely being viewed end-on.
- **Debug a shader by rendering its intermediate values as colour, not by
  watching for motion.** Packing gust / `wind_strength` / final bend into R/G/B
  answered in one screenshot what a dozen motion comparisons could not, because
  an always-on idle layer means *any* two frames differ — so a screenshot diff
  can never prove which link in the chain is dead. Same lesson as the NPC
  `y = -0.05` sink: get the machine to print the number.
- A parameter can be declared, plumbed through an autoload, written to
  `RenderingServer`, and *still never read by the shader*. `wind_speed` was
  dead for a long time while being tuned repeatedly. If changing a value
  changes nothing, confirm the shader actually references it before assuming
  the value is wrong.
- Autoload defaults overwrite `[shader_globals]` in `project.godot` at
  `_ready()`. Editing the project settings alone looks like it does nothing.
